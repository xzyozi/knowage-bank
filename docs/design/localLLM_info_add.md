## 提案の構成

```
Deep Research（外部APIモデル or サービス）
   └── 一次情報URL収集 + 事実確認 + ソース要約
              │
              ▼
       中間成果物（JSON or Markdown）
       ・検証済みURL一覧
       ・各ソースの要約
       ・事実関係の整理
              │
              ▼
       ローカル14B（Q4）
       ・HTML記事生成（テンプレート準拠）
       ・Q&Aセクション構成
       * 本文の日本語ライティング
       ・中間成果物の参考URLをそのまま埋め込み
```

## これが成立する理由

14B Q4 の弱点だった部分がDeep Researchで完全に補完されます:

| 14B Q4 の弱点 | Deep Research で解決 |
|--------------|---------------------|
| 参考URLのハルシネーション | 検証済みURLを事前に確定 |
| 事実の正確性 | ソース付き要約を入力に含める |
| Web検索能力の欠如 | 検索・取得はDeep Research側が担当 |
| マルチソース統合 | 要約済みの構造化データとして渡す |

一方、14B Q4 が得意な部分はそのまま活かせます:

| 14B Q4 が担当 | 理由 |
|--------------|------|
| HTML構造の生成 | テンプレート追従は得意 |
| 日本語の文章化 | 入力が正確なら出力品質も安定 |
| Q&A形式への変換 | パターンマッチ的タスク |
| 要点の要約 | 入力が整理済みなら圧縮は可能 |

## 設計上のポイント

### 中間成果物のフォーマット

Deep Research の出力を14Bに渡す際、以下のような構造化形式にすると精度が安定します:

```markdown
# リサーチ結果: {トピック}

## 結論（1-2文）
{Deep Researchが出した端的な結論}

## 検証済みソース
1. [{タイトル}]({URL}) - {1行要約}
2. [{タイトル}]({URL}) - {1行要約}
3. ...

## 事実関係
- {事実1}（出典: ソース1）
- {事実2}（出典: ソース2）

## 賛否・反応（claim-context-review用）
### 支持
- {論点}（出典: ...）
### 批判
- {論点}（出典: ...）
```

これなら14Bは「構造化入力 → テンプレートHTML」の変換に集中できます。

### `claim-context-review` も実現可能になる

Deep Researchが Phase 1〜4（主張把握・一次情報確認・反応収集・ノイズ識別）を担当し、14Bが Phase 6（出力整形・HTML化）を担当すれば、Skill全体が動きます。

```
claim-context-review の分担:
─────────────────────────────────
Phase 1-5: Deep Research
  ・URL読み込み
  ・一次情報探索
  ・主張マップ構築
  ・反応収集
  - ノイズフィルタ

Phase 6: ローカル14B
  ・構造化出力生成
  ・HTML記事化（qa-html-noteと連携）
```

## 懸念点と対策

| 懸念 | 対策 |
|------|------|
| Deep Research のレイテンシ | 非同期実行。記事作成は結果取得後にバッチ的に行う |
| Deep Research のコスト | 記事1本あたり1回の呼び出しに限定。日常的な単純質問は14B単独で処理 |
| 中間成果物のトークン長 | ソース数を5-8件に制限し、要約を1行に絞る |
| 2段階処理のオーケストレーション | スクリプトまたはワークフロー自動化で管理 |

## Skill定義の修正方針

現在のSkill定義を「単一モデルが全工程を自律実行する」前提から「2段階パイプライン」に書き換えることになります。具体的には:

1. **`qa-html-note`**: 「リサーチ入力あり/なし」で分岐を追加。入力ありなら参考URLはそのまま使用
2. **`claim-context-review`**: Phase 1-5を「外部リサーチ依存」と明示。出力整形のみがLLM担当
3. **中間フォーマット仕様**: 新しいドキュメントとして追加

## Deep Research MCP 運用上のアプローチと注意点

Deep Research MCP を使用して調査を行う際、検索対象のフィルタリングや意図した結果の取得のために、クエリの入力方法に工夫が必要です。

### 1. 具体的で明確なクエリの指定
調査エンジンは「テスト」といった曖昧な単語のみを与えると、検索対象が広すぎて検索と処理のループに陥り、ハングあるいは失敗しやすくなります。「何について調べたいか」を具体的に指定することで、おかしなループを回避して正しく高速に動作させることができます。

- **NG例**: `テスト`
- **OK例**: `MCP（Model Context Protocol）の概要と、主要なトランスポート（stdio, sse）の違いについて調査してください`
