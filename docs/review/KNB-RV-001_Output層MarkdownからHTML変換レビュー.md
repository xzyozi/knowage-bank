## 1. レビュー範囲

### 1.1 対象実装
- `src/app/article_builder.py`
- `src/app/utils/markdown_cleaner.py`
- `src/app/utils/markdown_parser.py`
- `src/app/utils/citation_processor.py`
- `src/app/templates/article_template.html`
- `public/styles/site.css`
- `src/scripts/sync-github-issues.py`

### 1.2 判断基準
定義済みのMarkdownレポートを、記事仕様書に準拠した安全な静的HTMLへ変換し、Issue起点のOutput処理から一貫して出力できることを判断基準とする。

## 2. 結論

`ArticleBuilder.build_article_html({"markdown_text": ...})` はMarkdown入力を受け付け、HTMLテンプレートへ組み立てる機構を持つ。そのため、入力構文を固定すれば、技術調査レポートを記事HTMLとして出力できる。

ただし、現行のIssue→記事生成スクリプトは構造化JSONを生成・受け渡ししており、Markdown変換経路へ接続されていない。さらに安全なHTML出力、入力検証、引用検証、既存JSON経路の実行時エラー対応が必要である。したがって、Markdown形式を正式なOutput入力とするには、後述の必須対応を完了することを条件とする。

## 3. 現状で出力可能な形式

| 入力要素                | 出力結果                         | 実装箇所                 |
| :---------------------- | :------------------------------- | :----------------------- |
| frontmatter             | タイトル、カテゴリ、リードの取得 | `FlexibleMarkdownParser` |
| `##` / `###` 見出し     | `h2` / `h3`                      | `FlexibleMarkdownParser` |
| 段落・リスト            | `p` / `ul` / `ol`                | `FlexibleMarkdownParser` |
| コードフェンス          | `pre > code`                     | `FlexibleMarkdownParser` |
| Pipe Table              | `table.figure`                   | `FlexibleMarkdownParser` |
| 定型参考文献・`[N]`引用 | 参考文献アンカーと再採番         | `citation_processor`     |

## 4. 必須対応事項

### 4.1 Markdown経路のOutput統合（最優先）

| 現状                                                | 課題                                                             | 対応方針                                                                            |
| :-------------------------------------------------- | :--------------------------------------------------------------- | :---------------------------------------------------------------------------------- |
| `sync-github-issues.py` は構造化JSONをLLMに要求する | `markdown_text` が渡されず、Markdownパーサー・引用処理を通らない | Markdown専用プロンプトと入力DTOを定義し、`ArticleBuilder` へ `markdown_text` を渡す |
| Stage 2の入力仕様がない                             | `citations_keep` と `citation_labels` の生成元が不明確           | LLM出力または後段の判定処理として責務・形式を定義する                               |

### 4.2 既存JSON経路の実行時エラー
`ArticleBuilder.build_article_html()` はMarkdown未指定時に `lead_text` を初期化しないまま参照する。現行Outputスクリプトの構造化JSON経路では `UnboundLocalError` となる可能性がある。Markdown経路へ移行するか否かにかかわらず、既存経路を安全に完了または廃止する方針を決める。

### 4.3 HTML・URLの安全性
Markdownパーサーは通常テキストや見出しなどをHTMLエスケープせず、テンプレートは `body_html | safe` を使用する。LLM出力・調査結果を入力とするため、許可リスト方式のHTMLサニタイズ、テンプレート変数の自動エスケープ、およびリンクURLのHTTPS scheme検証を導入する。

### 4.4 保存前後の検証
記事仕様書§16が規定するStage 5は未実装である。保存前に必須項目・禁止構文・見出し階層を検証し、保存後に本文の引用アンカーと参考文献IDの対応、参照URL、出力HTMLの基本構造を検証する。

## 5. 追加対応候補

| 機能                       | 現状                      | 方針候補                                  |
| :------------------------- | :------------------------ | :---------------------------------------- |
| H4以降                     | 段落扱い                  | 対応レベルを明文化し必要なら変換を追加    |
| ネストリスト・引用ブロック | 未対応                    | 許可構文へ追加する場合にパーサーを拡張    |
| 画像                       | 未対応                    | ローカルパス・`alt`・許可拡張子を検証     |
| Mermaid                    | DSLテキストを出力するのみ | 静的SVGへの事前変換または仕様対象外を決定 |
| 未閉鎖コードフェンス       | 検出なし                  | 入力エラーとして扱うか安全に補完          |

## 6. CSS・仕様の整合性
パーサーは `<table class="figure">` を出力する一方、CSSは `.figure table`、`.figure th`、`.figure td` を指定している。テーブル自体が `.figure` であり子孫`table`ではないため、セルの枠線・ヘッダー装飾が期待どおり適用されない。HTML出力またはCSSセレクタを統一する。

また、記事仕様書ではQ&A・要点・参考資料を必須とするが、Markdown経路ではすべて任意である。Markdown入力契約または保存前検証で必須性を保証する。

## 7. Markdown入力契約案

```markdown
---
title: "記事タイトル"
eyebrow: "カテゴリ > サブカテゴリ"
lead: "結論または概要。"
---

Q: 質問
A: 短い回答。

## 背景
本文。[11]

## 要点
- 要点1
- 要点2

[11] 公式ドキュメント
URL: https://example.com/docs
```

- 必須frontmatter: `title`、`eyebrow`、`lead`
- 必須セクション: Q&A、要点、一次情報の参考文献
- 許可構文: 見出し、段落、リスト、表、コード、HTTPSリンク
- 禁止構文: 生HTML、スクリプト、イベント属性、外部リソース、非HTTPSリンク
- 引用: 本文の`[N]`と末尾参考文献の番号を一致させる

## 8. 推奨実装順序
1. Markdown専用のLLMプロンプト、入力DTO、Outputスクリプトへの接続を実装する。
2. `ArticleBuilder` の既存JSON経路を安全に修正または整理する。
3. HTMLサニタイズ、URL検証、Markdown構文検証を実装する。
4. Stage 5として必須項目・引用アンカー・HTML構造の検証を実装する。
5. テーブルCSSを出力HTMLに合わせる。
6. パーサー境界テストとIssue処理からHTML保存までの結合テストを追加する。
7. Mermaid・画像・高度なMarkdown構文の対応範囲を決定する。

## 9. 追加された実データ形式による再評価

### 9.1 入力データの分類
- `data/tmp/*.md` は、目次・調査概要・H1〜H3・本文・リスト・表・本文内引用・末尾の番号付き参考文献を持つ**調査レポートMarkdown**である。
- `data/issue_status.json` はIssue同期状態を保持する永続化データであり、記事本文・引用・表示メタデータを持たないため、HTML記事生成の直接入力には用いない。

### 9.2 実データとの適合性
調査レポートMarkdownの本文構造は、既存の目次／調査概要除去、H1〜H3、リスト、表、インライン装飾、`[N]`引用、`[N] タイトル` + `URL:` の参考文献分離に適合する。したがって、本文と引用付き参考文献をHTML化する目的に限れば、入力サンプルは高い適合性を持つ。

ただし、入力サンプルにはfrontmatter、`eyebrow`、リード文、Q&A、要点がない。先頭H1は記事タイトルとして利用できるが、H1直後がH2で始まるため、現行のリード抽出では空文字となる。また、参考文献の直前にある `## 出典` 見出しは、参考文献ブロックだけを分離する現実装では空の見出しとして本文に残る。

### 9.3 再評価の結論
**調査レポートMarkdownを受け入れる方式なら、実現可能性は「条件付きで可能」から「本文変換は実現可能、記事化には正規化が必須」へ具体化される。** パーサーを全面的に置き換える必要はないが、調査レポートを記事DTOへ変換する専用の前処理境界を設ける必要がある。

推奨する責務分離は次のとおりとする。

```text
調査レポートMarkdown
  → 調査レポート正規化（目次・調査概要・出典見出しの除去、構造検証）
  → 記事メタデータ補完（カテゴリ、リード、Q&A、要点、引用採否）
  → Markdown→HTML変換・引用アンカー生成
  → 記事仕様の必須要件と安全性の検証
  → 保存
```

メタデータ補完は、Markdownへfrontmatterを必須追加する方式、またはIssue情報・LLM出力を別DTOとして受け取る方式のいずれかを採用する。調査レポートをそのまま保持する目的では、後者を推奨する。

## 10. 完了判定
Markdown入力から、記事仕様書に定めるヒーロー、Q&A、本文、要点、参考文献、ナビゲーションを含むHTMLを生成し、安全性・必須項目・引用アンカーを検証したうえで保存できることを、Output層のMarkdown対応完了条件とする。

## 11. 方針決定：Markdown中心のレポート表示

### 11.1 表示方針
調査レポートMarkdownの内容は、記事用のQ&A・要点・サマリーへ全面的に再構成せず、本文・見出し・リスト・表・コード・引用を可能な限りそのまま表示する。Output層は、情報を要約・削除して定型記事へ変換する層ではなく、Markdownの構造を静的HTMLへ安全に投影する層として扱う。

既存のHTMLテンプレートは閲覧ページの外枠として使用するが、Q&Aおよび要点は入力に存在する場合のみ表示する任意セクションとする。レポート入力に存在しないことをエラーにせず、記事仕様書の必須要件はレポート表示モードに合わせて見直す。

### 11.2 表示を絞る対象
以下は内容を要約する目的ではなく、閲覧性と参照整合性のために限定的に整理する。

- 目次、重複する調査メタ情報、参考文献直前の空見出しを除去する。
- 先頭H1をページタイトルとして使用し、本文中の重複H1は出力しない。
- 本文中の`[N]`引用を参照アンカーへ置換し、末尾参考文献を採番済みリストとして出力する。
- 不正な構文、危険なHTML、許可されないURLは拒否または無害化する。

### 11.3 メタデータの扱い
`title` は先頭H1から取得可能とする。`eyebrow` はIssue情報または既定カテゴリを用い、`lead` は入力にfrontmatter等で指定された場合のみ表示する。入力にないQ&A、要点、タグ、関連リンクをOutput層が生成必須とすることは避ける。

### 11.4 実装上の再整理
この方針では、調査レポート→記事DTOへの内容再構成は必須ではない。代わりに、次の軽量な境界を実装対象とする。

```text
調査レポートMarkdown
  → 表示用正規化（表示不要な部分の除去、構造・安全性の検証）
  → Markdown→HTML変換・引用アンカー生成
  → 保存
```

HTMLサニタイズ、URL検証、未閉鎖コードフェンス検出、引用アンカー整合性検証は、Markdown主体の方針でも必須である。

## 13. 方針決定：JSONを不要とするMarkdown直接入力

### 13.1 外部入力契約
Output層の外部入力はMarkdown本文のみとし、LLMへ記事用JSONを要求しない。変換処理の途中でタイトル・参考文献・本文HTMLなどを保持する内部データ構造を使用してもよいが、それは実装詳細であり、入力ファイルやLLM出力の契約にはしない。

タイトルは先頭H1、本文はMarkdown構造、参考文献は末尾の番号付き出典から取得する。カテゴリやリードなど、Markdownに存在しない任意の表示項目は表示を省略するか、明示的な既定値を用いる。入力にない記事要素をJSONやLLMで補完することを必須にしない。

### 13.2 CSSを確実に適用する変換契約
MarkdownをそのままHTMLへ流し込むのではなく、パーサーがCSSに対応する限定されたHTML構造を出力する。Markdownの見た目や任意のHTML classを入力側へ要求しない。

| Markdown構文   | 出力HTML                                                   | CSS適用方針                                              |
| :------------- | :--------------------------------------------------------- | :------------------------------------------------------- |
| 先頭H1         | テンプレート内の `header.hero > h1`                        | ページタイトルとして一度だけ表示                         |
| H2 / H3        | `article-body > h2` / `h3`                                 | 既存タイポグラフィを適用                                 |
| 段落・リスト   | `p` / `ul` / `ol`                                          | 記事本文の標準余白を適用                                 |
| コードフェンス | `pre > code`                                               | 既存コードブロックCSSを適用                              |
| Pipe Table     | `<div class="figure table-wrapper"><table>…</table></div>` | 現行の `.figure table`、モバイル横スクロールを確実に適用 |
| 参考文献       | `section.related > ol`                                     | 既存の参考資料スタイルを適用                             |
| Mermaid        | 変換済みSVGを `figure.figure` として出力、またはコード表示 | CSSだけで図を描画しない                                  |

テーブルは現行の `<table class="figure">` ではなく、`.figure` をラッパー、内側を標準の`table`とする。これにより既存CSSの `.figure table`、`.figure th`、`.figure td` と一致し、デスクトップ・モバイルの両方で意図した装飾が適用される。

### 13.3 信頼するMarkdownの扱い
Markdownの内容・構造を信頼して保持する方針と、任意の生HTMLを無制限に許可することは分ける。本文内容は保持しつつ、HTMLはパーサーが生成する許可済みの要素・属性に限定する。これにより、CSSの適用対象を安定させ、意図しない`style`属性・`script`・外部リソースによる表示崩れを防ぐ。

## 15. 実データによる変換検証と反映結果

`data/tmp` 配下の調査レポートMarkdownを、現行の `ArticleBuilder.save_article()` を用いて `public/articles/preview-research-report.html` に出力した。

初回出力では、目次が残存し、`# 目次` がページタイトルとして出力された。原因は目次除去用正規表現が、見出し後の空行および番号形式 `1.` を受理しなかったことである。

以下を修正した。

- 目次除去処理で、見出し後の空行、`1.`、`2.1` 形式の番号を許容した。
- 参考文献分離後に空になる末尾の「出典」「参考文献」「参考資料」見出しを除去した。
- 表の出力を `<div class="figure table-wrapper"><table>…</table></div>` に変更し、既存CSSの `.figure table`、`.figure th`、`.figure td` と整合させた。
- リード文が存在しない場合は空の `.lead` 要素を出力しないようにした。

再生成では、先頭の調査レポート見出しがページタイトルとして出力され、目次・空リード・空の出典見出しが除去された。本文、表、引用アンカー、参考文献リストは保持された。
